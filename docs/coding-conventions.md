# Coding Conventions — Dynamic Scheduler Backend

## 1. Java 코드 스타일

- 기존 파일의 들여쓰기와 중괄호 스타일을 유지한다.
- 새로운 Java 코드는 기본적으로 탭 들여쓰기를 사용한다.
- 동일 블록에서 탭과 공백을 임의로 혼용하지 않는다.
- 짧은 조건식, 메서드 선언, 반환문은 가독성이 허용하면 한 줄로 작성한다.
- 긴 조건식이나 메서드 인자는 적절히 줄바꿈한다.
- 필드, 생성자, 메서드 사이에는 적절한 공백 줄을 둔다.
- 기존 파일 전체를 불필요하게 포맷팅하지 않는다.

### 네이밍

- 클래스: PascalCase
- 메서드 및 변수: camelCase
- 상수: UPPER_SNAKE_CASE
- 기존 프로젝트의 클래스 및 메서드 네이밍 패턴을 우선한다.

## 2. 의존성 주입

- Spring Bean은 생성자 주입을 기본으로 한다.
- 의존성 필드는 `private final`로 선언한다.
- 기존 명시적 생성자 작성 패턴을 우선한다.
- 불필요한 필드 주입이나 setter 주입을 추가하지 않는다.
- Quartz Job도 기존 생성자 주입 방식과 Spring 연동 구조를 확인한 후 작성한다.

## 3. 레이어별 작성 규칙

### Controller

- Controller는 HTTP 요청 및 응답을 담당한다.
- 업무 로직은 Service에 위임한다.
- 기존 `ResponseEntity` 사용 패턴을 유지한다.
- 기존 API URL, HTTP Method 및 응답 형식을 임의로 변경하지 않는다.
- 기존 Controller의 메서드 네이밍 패턴을 따른다.

### Service

- Service는 업무 흐름, 유효성 검증, Mapper 호출 순서를 담당한다.
- 반드시 존재해야 하는 조회 결과는 null 여부를 검증한다.
- 주요 업무 단계는 `// 1. ...`, `// 2. ...` 형식으로 구분한다.
- 단순 로직을 불필요하게 여러 메서드나 클래스로 분리하지 않는다.

### DTO

- DTO는 데이터 전달 역할에 집중한다.
- 기존 Lombok `@Data` 사용 패턴을 우선한다.
- Java 필드명은 camelCase를 사용한다.
- PostgreSQL BIGINT 식별자는 일반적으로 `Long`을 사용한다.
- 시간대 정보가 없는 TIMESTAMP는 기존 `LocalDateTime` 매핑을 따른다.

## 4. MyBatis 작성 규칙

- Mapper 인터페이스에는 `@Mapper`를 사용한다.
- 여러 SQL 파라미터는 `@Param`으로 명확하게 구분한다.
- Mapper XML namespace와 메서드명을 인터페이스에 일치시킨다.
- Mapper 메서드명은 기존 `find...`, `get...` 패턴을 따른다.
- 단순 조회는 기존 설정을 활용하여 `resultType`을 우선 검토한다.
- 복잡한 매핑이 필요한 경우 `resultMap`을 사용한다.
- SQL은 `SELECT *` 대신 필요한 컬럼을 명시한다.
- SQL 값 바인딩은 `#{}`을 우선 사용한다.
- XML의 SQL 들여쓰기와 줄바꿈은 기존 파일 스타일을 따른다.
- 안정적인 정렬이 필요하면 PK 등의 보조 정렬 기준을 검토한다.
- nullable 파라미터는 필요한 경우 `jdbcType`을 명시한다.

## 5. 주석·예외·로깅 스타일

### 주석

- 주요 업무 처리 단계는 번호 주석으로 구분한다.
- 복잡한 로직은 구현 이유와 목적을 설명한다.
- 필요한 경우 공개 메서드에 Javadoc을 작성한다.
- 단순한 코드를 그대로 설명하는 불필요한 주석은 피한다.

### 예외

- 업무 예외 메시지는 한글로 구체적으로 작성한다.
- 원인 예외가 중요한 경우 cause를 유지한다.
- 기존 예외 처리 패턴을 따른다.
- 예외 메시지에 민감 정보를 포함하지 않는다.

### 로깅

- 기존 SLF4J 로깅 패턴을 따른다.
- 문자열 연결보다 `{}` 플레이스홀더를 우선 사용한다.
- 필요한 경우 실행 식별자를 함께 기록한다.
- 디버깅에 필요한 예외 스택 트레이스를 적절히 남긴다.
